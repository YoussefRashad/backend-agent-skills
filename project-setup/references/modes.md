# Modes

`detect.mjs` proposes a mode with evidence. You confirm it after reading the files; the user approves it in
the Phase 0 summary. When evidence is weak, choose the more conservative mode (`adopt` over `migrate-v1`).

| Mode | Evidence required | Behaviour |
|---|---|---|
| `fresh` | No instruction files, no `.ai/`, source code present | Full generation |
| `empty-repo` | No tracked source files | Minimal setup only (see below) |
| `migrate-v1` | v1 provenance comment `Generated by project-setup` in `CLAUDE.md` or `.ai/**` | `references/migration-v1.md` |
| `adopt` | Existing `CLAUDE.md`/`AGENTS.md`/`.ai/`/agents **without** reliable provenance | Conservative merge |
| `add-claude` | `AGENTS.md` exists, no `CLAUDE.md` | Add CLAUDE.md wrapper + `.claude/*`; adopt AGENTS.md content |
| `update` | Valid `.ai/manifest.json` (`schema: 2` from v2, or `schema: 3`) | Drift-aware regeneration; from schema 2 also `references/migration-v2.md` |
| `invalid` | `.ai/manifest.json` present but invalid | Stop; repair or restore the manifest first |

`.ai/` existing on its own is **not** proof of v1. Neither are files named `reviewer.md`.

A valid schema-2 manifest is a v2 installation that needs an update (detect reports `needs update`). Every commit
writes manifest schema 3; schema 2 is accepted only as update input. Invalid metadata is repaired through the
documented procedure first; it is never permission to infer or invent ownership.

## Conflicts: meaning, not text

`AGENTS.md` and `CLAUDE.md` are supposed to differ (shared vs Claude-only). Stop and ask only when:

- the same topic carries contradictory instructions (e.g. "use ORM migrations" vs "DDL is applied manually");
- the same command, path, or limit has different values;
- merging would drop or weaken content (a rule present in one file disappears from the merged result);
- a rule exists only in `CLAUDE.md` but is clearly tool-neutral; propose moving it, do not move it silently.

Present each conflict as: file A line, file B line, proposed resolution, what is lost if accepted.

## Per-mode notes

**fresh.** Generate everything in `references/docs-generation.md` that the evidence supports. Skip files that
would be empty; skip `business-rules/` if the domain is unclear.

**empty-repo.** Create `AGENTS.md` (overview, critical-rules, agents blocks only), `CLAUDE.md`, the agent
definitions and wrappers, `.claude/settings.json` denies, `.gitignore` block, `TODO.md`. Do not create context
docs, ADRs, or business rules. Record "re-run project-setup once code exists" in `TODO.md`.

**adopt.** Treat every existing line as user-owned. Introduce managed blocks only for new sections. If the root
`CLAUDE.md` holds tool-neutral rules and there is no `AGENTS.md`, propose (do not perform without approval)
moving them into `AGENTS.md` and leaving `@AGENTS.md` plus Claude-only content in `CLAUDE.md`. Show exactly
which lines move.

**backend-standards adoption.** For a backend-standards-shaped CLAUDE.md, setup MUST preserve
the BS-marked block as project content, including hand edits. BS markers do not grant
project-setup ownership; treating them as its own markers could erase standards or local decisions.

Setup MUST keep the @-imports of .ai/standards/ in CLAUDE.md and retain the human-facing
standards version line. Codex treats those imports as plain text, so moving them into AGENTS.md
would not preserve Claude's import behavior. Shared rules may be proposed separately, with
explicit approval, without removing those imports or the version line.

Setup MUST offer the existing reviewed replacement for BS standalone reviewer and docs-sync
files in .claude/agents/. Before replacement, inventory their rules, including frontmatter settings
such as model and tools, and obtain a disposition for every customization. Move approved review
rules to ".ai/agents/reviewer.project.md" and approved documentation rules to
".ai/agents/docs-sync.project.md". Preserve existing extension bytes and request merged ownership,
so the wrapper replacement does not discard project rules.

A conflicting rule MUST remain pending until explicitly resolved. Approval cannot make a
project rule relax a canonical restriction. If replacement is declined, keep the installed
file and report the incomplete agent update; do not claim the PS agent layer is fully installed.

Validate checks backticked or linked references inside project extensions. Moved text that
references absent docs fails validation until fixed. Setup MUST report that failure and obtain
a reviewed correction, so adoption cannot claim a valid installation with broken references.

Source inspection confirms that existing Claude instructions or agents without a valid manifest
or v1 provenance select adopt. A valid manifest selects update, and invalid metadata selects
invalid. A BS name or marker is not v1 provenance.
This behavior has not been verified on a real backend-standards scaffold.

**add-claude.** Leave `AGENTS.md` content intact; add managed blocks only where sections are missing. Create
`CLAUDE.md` as `@AGENTS.md` plus the `claude` block.

**update.** For every manifest entry run `blocks.mjs drift` (or compare the full-file hash):
- `unchanged`: regenerate only if something the content is derived from changed (code, config, or the skill's
  templates). Never rephrase unchanged facts: a re-run with no such change must produce zero diff (measured live in
  Codex: 15 drafts identical, commit reported zero diff).
- `edited-by-user` / user-modified full file: show the user's edit next to the new content and ask: keep theirs,
  take new, or merge. Never decide silently.
- `removed-by-user`: do not re-add; ask.
- marker errors: stop; ask the user to repair markers first (show line numbers).
Bump nothing if the outputs are identical: a no-op run must produce zero diff, including the manifest.

From a schema-2 manifest, also follow `references/migration-v2.md`: verify the shipped v2.0.0 comparison data with
`scripts/check-agent-baselines.mjs` before comparing installed agents or wrappers, give every installed
customization an explicit disposition, and run the policy migration and the complete runtime unit in the same
reviewed transaction. A schema-3 project is never repaired with v2 commands.

## Running from either tool

Either tool may run the full setup and draft files for both. A run from Codex cannot prove Claude loads its
files, and vice versa; the report marks the other tool as *not verified* until it is checked there.
